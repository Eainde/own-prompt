<instructions>
1. Locate every page that contains an ownership chart (boxes connected by arrows depicting corporate ownership). Note the page number(s). If the document has multiple charts, treat them separately.

2. ENTITY ENUMERATION — For every entity (corporate entity or natural person) visible as a labeled box, text node, or named element in a chart:
   - name: EXACTLY as written in the chart (preserve casing, spelling, punctuation, suffixes). Do NOT correct, normalize, or expand.
   - type_hint: "corporate_entity" (name contains Limited, Ltd, Inc, Pte, LLC, GmbH, S.A., or similar corporate suffix) | "natural_person" (name pattern looks like an individual's name) | "unknown" (cannot tell from name alone).
   - vertical_position: TOP | UPPER_MIDDLE | MIDDLE | LOWER_MIDDLE | BOTTOM (5-point scale based on its placement in the chart).
   - horizontal_position: LEFT | CENTER_LEFT | CENTER | CENTER_RIGHT | RIGHT (5-point scale based on horizontal placement).
   - chart_id: identifier for the chart this entity belongs to (e.g., "page_1_chart"). Same string for all entities in the same chart.
   - associated_label: any percentage label that is attached to the entity's box (NOT to an arrow). E.g., a "100%" label INSIDE or DIRECTLY adjacent to the entity's box. Set to null if no such label.
   - evidence: one-line spatial description (e.g., "labeled box in column 3, upper-middle area of page 1 chart").

3. ARROW ENUMERATION — For every arrow visible in any chart:
   - from: the name of the entity at the arrow's TAIL (the end WITHOUT an arrowhead). MUST be a specific named entity from entities[] — NEVER a collective noun like "group of persons", "cluster", "column", or "shareholders".
   - to: the name of the entity at the arrow's HEAD (the end WITH the arrowhead — the pointy end). MUST be a specific named entity from entities[].
   - label_percentage: the percentage attached to the source shareholder (read from the % label adjacent to THAT specific shareholder's name, NOT a group total), or null if no % is visible.
   - chart_id: which chart the arrow is in.
   - evidence: a one-line spatial description of the arrow's path AND where the arrowhead is located (e.g., "vertical line from lower edge of Phoenix Ventures box down to upper edge of Brandix Lanka box; arrowhead is at the BOTTOM end, pointing DOWN at Brandix Lanka").
   - direction_confidence: HIGH (arrowhead clearly visible, direction unambiguous) | MEDIUM (arrowhead small or partial but discernible) | LOW (direction ambiguous, your best guess) | UNKNOWN (no arrowhead visible — line connector only).

   BRACKET HANDLING (CR.R9 + CR.R12 — CRITICAL):
   If a group of shareholders is connected to a company via a BRACKET (a horizontal/vertical line spanning multiple shareholders that joins into a single line ending at the company), you MUST output ONE arrow PER shareholder — never a single "group" arrow.
   - For each shareholder enclosed by the bracket, create an arrow where from = that individual's name, to = the company at the bracket's terminus.
   - bracket_members (REQUIRED, per CR.R12) is the array of ALL shareholder names enclosed by that bracket. Every arrow derived from the same bracket MUST have IDENTICAL bracket_members. NO placeholders ("and N others", "...", "etc.", "the rest") — list every name. If you cannot name them all, the bracket boundary is unclear and you MUST set direction_confidence=LOW and add the target to flagged_targets per CR.R11.
   - For a direct simple arrow between two corporate entities (no bracket), bracket_members = [arrow.from] (single-element array).
   - The evidence MUST name the OTHER shareholders inside the same bracket explicitly so the assignment is auditable. Format: "Bracket on page N connects [THIS SHAREHOLDER] ([%]) together with [OTHER SHAREHOLDER 1] ([%]), [OTHER SHAREHOLDER 2] ([%]), [OTHER SHAREHOLDER 3] ([%])... into a single joining line ending at [COMPANY]. Arrowhead at the joining line's [end] pointing [direction] at [COMPANY]. This arrow represents [THIS SHAREHOLDER]'s connection." DO NOT write "and N other individuals" — list them by name. If you write a placeholder, you are emitting a CR.R12 violation that the pipeline will reject.
   - The arrow's label_percentage is THIS individual shareholder's percentage (not the group total).
   - CROSS-CHECK BEFORE EMITTING: for each target T, count how many distinct shareholders you placed inside T's bracket(s). That count MUST equal both (a) the number of arrows you emit with to=T, AND (b) the length of bracket_members on each such arrow, AND (c) sum_check.per_target_sums[T].shareholder_count. If any of these three counts disagree, you've contradicted yourself — re-trace before emitting.
   - The downstream extractor CANNOT decompose a group arrow back to per-shareholder assignments — it will guess by visual proximity and contaminate branches. Do NOT make it guess.

4. ARROW DIRECTION DISCIPLINE:
   - The TAIL of an arrow is the end WITHOUT the arrowhead. The HEAD is the pointy end WITH the arrowhead.
   - from = entity at tail. to = entity at head.
   - If you cannot see an arrowhead clearly, set direction_confidence to UNKNOWN. The downstream agent will handle the ambiguity.
   - Do NOT infer direction from spatial position ("parents are at top"). Do NOT infer from percentage label position ("the % is near the owned entity"). Do NOT infer from real-world knowledge ("Big Corp owns Small Co in reality"). USE ONLY the visible arrowhead.
   - In dense areas of the chart with many arrows, trace each one individually. Do NOT batch-assume.

5. ANTI-BIAS REMINDERS:
   - The document may contain emails, certificates, headers, and footers mentioning entities prominently (e.g., "Periodic Review of XYZ Limited"). IGNORE all of that. Your output reflects ONLY what is visually in the chart.
   - If you recognize an entity name as a famous real-world company, IGNORE that recognition. Use only what the chart shows.
   - You are not extracting ownership. You are describing pixels. Stay descriptive.

6. CHART NOT FOUND:
   - If the document has no ownership chart, set entities = [], arrows = [], charts = [], and notes = "No ownership chart found in document."
   - If the document has only a textual ownership description, set entities = [], arrows = [], and notes = "Document contains textual ownership description but no visual chart. Downstream agent should extract from text."

7. PER-TARGET SUM CHECK (CR.R10 — MANDATORY FIELD, schema enforces):
   You MUST populate the top-level `sum_check` field of your output. Steps:
   (a) Compute per_target_sums: for every entity that appears as `to` of at least one arrow, sum the numeric values of incoming arrows' label_percentage. Output one {target_entity, sum_percentage, shareholder_count} per such entity.
   (b) Compute flagged_targets: for every target whose sum is outside [95%, 105%], add its name to flagged_targets. These are the contamination signals.
   (c) Set overall_status: "CONSISTENT" if flagged_targets is empty and all assignments confident. "INCONSISTENT" if any target's sum is materially off OR you guessed bracket membership without clear visual basis. "PARTIAL" only if the source document explicitly documents partial ownership info.
   (d) If overall_status = INCONSISTENT, the notes field MUST describe which brackets you could not confidently trace, what your best guesses were, and why the visual was ambiguous (small font, overlapping connectors, etc.).
   (e) DO NOT fake CONSISTENT to pass the check. The downstream extractor will recompute sums and the critic will compare your reported sums vs computed. Deception is caught and flagged as a CR.R10 violation.

8. BRACKET TRACING HONESTY (CR.R11):
   If you cannot clearly see which shareholders are inside a specific bracket, do NOT use horizontal_position as your sole assignment basis. Either set the affected arrows' direction_confidence = "LOW" (so extraction refuses to create those edges) OR add the target to flagged_targets and set overall_status = INCONSISTENT. The pipeline will retry chart_reader (different model, different prompt) rather than propagate guesses. Honesty is auditable; silent guessing causes downstream branch contamination.

9. OUTPUT — Return strictly valid JSON matching the provided schema (including the required sum_check object). No commentary, no markdown, no explanation outside the JSON.
